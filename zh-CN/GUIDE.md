# UI 设计与开发人机协作经验与避雷指南

> **作者：**梁卓滢（Cher Liang）  
> **版本：**1.0.0 · 2026 年 9 月 26 日  
> 用途：在设计或实现网页、桌面工具、工作台、弹窗、浮窗和交互组件时，作为用户、AI、设计师与开发者的共同协作基准。  
> 目标：既保留从 0 到 1 的视觉创造力，也避免覆盖式修补、图层误伤、坐标误判、重复 CSS、状态不同步和“局部测试冒充完成”。  
> 适用：全新视觉设计、现有产品大改版、局部 UI 修复、UX 交互调整、视觉资产制作和跨平台适配。

---

## 1. 这份手册管什么，不管什么

本手册约束的是：

- 实现过程是否干净、可维护。
- 是否真正理解用户要的交互。
- 是否修改了正确的页面和源码。
- 是否完成真实用户链路验证。
- 是否把正式资产和失败版本分开。

本手册不限制：

- 视觉风格和创意方向。
- 配色、构图和品牌表达。
- 是否使用极简、文化、现代、实验性或其他风格。
- 从 0 到 1 时提出大胆的新方案。

防错规则不能被用来拒绝创意。创意可以开放，实现必须严谨。

---

## 2. 开始前先判断是哪类任务

不同任务不能套用同一种僵硬流程。

### 2.1 从 0 到 1 的全新设计

此时可能没有正式页面、截图、设计系统或现成代码，这是正常情况。

模型应从以下信息中尽量推进：

- 产品要解决什么问题。
- 谁会使用。
- 最常做的任务是什么。
- 希望给人什么感觉。
- 有哪些内容、品牌、设备或技术限制。

信息不足时，模型应主动提出少量关键问题或合理假设，不能要求用户先准备完整设计规范。

如果视觉方向差异较大，优先询问：

> 这次属于较大的视觉决策，要不要先做一张草稿图／线框图，确认方向后再写正式代码？

这是一项优先建议，不是绝对要求。用户明确希望直接开发时，可以直接进入代码，但需要说明采用的设计假设。

从 0 到 1 时，模型可以提出 2–3 个真正不同的方向，例如：

- 更克制、效率优先。
- 更有品牌和文化氛围。
- 更轻、更现代、更适合高频操作。

不能只给三个颜色略有不同、结构完全相同的假方案。

### 2.2 现有产品的大改版

需要先识别：

- 当前正式页面和真实运行版本。
- 哪些信息结构仍要保留。
- 哪些视觉可以推翻。
- 哪些数据、功能和用户习惯不能丢。

大改版同样优先提供草稿图／视觉预览，因为直接改代码的返工成本较高。

### 2.3 现有产品的局部修复

例如：

- 改一个页头颜色。
- 调小按钮或字号。
- 修复残边、错位和点击问题。
- 调整弹窗拖动与滚动。

此时应严格控制修改范围，不能顺手重做已确认的其他部分。

## 3. 专业词汇可以使用，但用户不需要先成为前端工程师

模型可以正常使用专业词汇，例如：

- `margin`
- `padding`
- `display: flex`
- `display: grid`
- `position: fixed`
- `position: absolute`
- `overflow`
- `z-index`
- `max-width`
- 响应式断点

保留专业词汇有好处：

- 用户可以更精确地指挥后续修改。
- 方便检查模型究竟改了什么。
- 用户可以逐步建立设计和开发判断力。
- 避免模型用含糊语言隐藏实现细节。

但模型不能要求用户在不理解时自己猜参数。

正确协作方式是：

1. 模型提出专业方案和推荐参数。
2. 同时说明它会造成什么可见变化。
3. 用户理解时可以直接决定。
4. 用户询问术语时，模型再用大白话解释，并结合当前页面举例。

例如：

> 我建议把卡片容器改成 `display: flex`，并给底部按钮设置 `margin-top: auto`。这样无论每张卡文字多少，按钮都会自动贴齐卡片底部。

如果用户问“`margin-top: auto` 是什么”，再解释：

> 它会把按钮上方剩余空间全部占掉，相当于自动把按钮推到底部，不需要人工给每张卡写不同距离。

模型不应：

- 为了显得容易而完全隐藏实现方式。
- 一次堆出大量术语却不说明视觉影响。
- 把多个技术选项丢给用户，自己不做推荐。
- 因用户没有给出精确像素值而停止推进。

## 4. 用户和模型分别负责什么

### 用户更适合决定

- 喜不喜欢。
- 想让页面给人什么感觉。
- 哪些信息最重要。
- 哪些行为符合自己的使用习惯。
- 是否接受一次较大的视觉变化。

### 模型更适合负责

- 把感觉转成布局、字体、间距、层级和交互方案。
- 推荐 `margin`、`display`、尺寸和断点等参数。
- 解释各方案的视觉和维护代价。
- 找到当前源码中的唯一实现位置。
- 删除被替代的旧规则。
- 做静态检查和自动回归。

不要把本应由模型完成的技术设计工作退回给用户。

---

## 5. 视觉大改优先先看草稿

以下情况适合先做草稿图、线框图或视觉预览：

- 从 0 到 1 创建新产品。
- 页面信息架构发生明显变化。
- 整体品牌、配色或排版方向要改变。
- 需要重做导航、总览、结果页或复杂浮窗。
- 用户用语言描述了感觉，但还无法想象最终效果。
- 代码修改成本明显高于草稿验证成本。

草稿阶段应确认：

- 整体构图。
- 信息层级。
- 视觉气质。
- 主要交互入口。
- 内容密度。
- 宽屏与小屏的大致关系。

草稿阶段不必纠结：

- 每一个像素值。
- 最终动画参数。
- 完整错误状态。
- 所有边缘案例。

草稿确认后，再把视觉方向落实为可维护代码。

## 6. 修改既有 UI 时的五条铁律

1. **修改源头，不覆盖结果。**
2. **删除旧实现，不叠加补丁。**
3. **先定义交互状态，再写视觉样式。**
4. **验证完整用户链路，不用局部测试冒充完成。**
5. **已确认视觉默认保持，一次只改授权范围。**

这些铁律主要针对已有 UI 的修改和修复，不用于限制从 0 到 1 的视觉探索。

---

## 7. 禁止用新色块或新图层掩盖旧设计

### 错误做法

- 在旧页头上再放一个新色块，假装改了颜色。
- 用背景矩形遮住不想显示的文字或边缘。
- 用伪元素遮住旧圆角、旧边框、错误文字或残留素材。
- 保留旧 DOM，再加一套相似 DOM 显示新版。
- 为了让补丁生效，不断追加 `!important`。
- 旧事件仍在运行，再加一个新监听器修补。

常见后果：

- 露出旧颜色和浅色边缘。
- 出现白边、矩形残留和双重圆角。
- `×` 看得见却无法点击。
- 隐形层挡住下面的按钮。
- 下一次修改无法判断哪条规则真正生效。

### 正确做法

- 改颜色：修改原元素的 `background`、`color`、`border`。
- 改尺寸：修改原布局和盒模型。
- 删除内容：删除对应 DOM、背景图或状态分支。
- 改交互：移除旧监听器，再保留唯一的新逻辑。
- 换资产：正式运行文件只保留一个明确版本。
- `::before`／`::after` 可以用于职责明确的背景、装饰或状态层；它们的问题不在于“使用伪元素”，而在于是否被拿来掩盖旧错误、模拟删除内容或长期修补正式资产。

一句话原则：

> 修改原来的东西，而不是在原来的东西上面再盖一个东西。

## 8. 局部修改前列出变化与保持项

可以使用下面的简单格式：

```text
本次改变：
- 阅读框页头再细一点。

必须保持：
- 阅读框宽度。
- 正文字号。
- 拖动范围。
- 框内／框外滚动关系。
- 关闭按钮行为。
```

如果用户只要求“页头再细一点”，模型不应同时改变：

- 弹窗宽度。
- 正文字号。
- 圆角。
- `×` 的形状。
- 页面打开方式。

当某个附带变化在技术上不可避免时，应先解释原因。

---

## 9. 先理解页面上下文，再理解组件

“独立阅读框”不一定等于“独立网页”。实现前应确认：

- 原页面是否继续可见？
- 新内容是跳转、弹窗、抽屉还是浮动窗口？
- 关闭后回到哪里？
- 刷新后恢复什么？
- 启动产品时应进入完整工作台还是内部结果页？

用户没有要求跳转时，不要擅自创建第二个页面。

如果用户要求“在当前工作台上方打开”，就应保留工作台上下文，而不是打开只剩结果内容的单独页面。

---

## 10. 浮窗、弹窗和阅读框需要完整交互模型

不能只实现“它出现了”。还要考虑：

### 打开

- 从哪里打开？
- 原页面位置是否保留？
- 默认尺寸和位置是什么？
- 默认滚动焦点属于哪里？

### 关闭

- `×` 是否始终可见？
- 点击区域是否足够？
- 是否被拖动逻辑或透明层挡住？
- Esc 或点击背景是否关闭？没有需求时不要擅自添加。

### 拖动

- 哪一部分是抓取区？
- `×` 和按钮不能误触拖动。
- 移动范围是组件容器、应用画布还是整个浏览器？
- 是否允许部分移出底部？
- 移出后保留什么区域供用户抓回来？
- 用户不需要缩放时，不增加拉拽缩放。

### 滚动

- 点击框内时滚动框内内容。
- 点击框外时是否交还页面滚动。
- 两层滚动条必须职责清楚。
- 不能通过移动浮窗来模拟内容滚动。

---

## 11. 卡片和列表应通过结构对齐

并列卡片正文长度不同时，底部按钮不应跟着文字漂移。

一种常见方案：

```css
.card {
  display: flex;
  flex-direction: column;
}

.card-action {
  margin-top: auto;
}
```

它的视觉效果是：按钮上方自动吸收剩余空间，因此每张卡的按钮都会贴齐底部。

不要：

- 给每张卡写不同的 `margin-top`。
- 用空行或透明文字撑高度。
- 只用一组固定文案检查对齐。

## 12. 数据型 UI 应先整理状态

上传、材料盒、收藏、任务结果和账号连接通常包含：

```text
初始空状态
已有数据
多项数据
正在处理
成功
失败
刷新恢复
重新启动恢复
删除单项
清空全部
失去连接
旧结果保留
```

模型应主动整理状态，不要求用户用技术语言枚举。

每个状态要明确：

- 显示什么。
- 哪些按钮可用。
- 数据来自浏览器、服务端还是本机文件。
- 失败时保留什么。
- 刷新后恢复什么。

---

## 13. 删除和清空必须验证完整链路

真正的验收链路是：

```text
点击按钮
→ 事件处理器执行
→ 请求方法和 URL 正确
→ 服务端收到请求
→ 持久储存改变
→ 服务端返回新状态
→ 前端更新状态
→ DOM 立即重绘
→ 刷新后仍正确
```

以下证据不能单独证明 UI 已完成：

- 储存层单元测试通过。
- 接口能被命令行调用。
- 后端文件已经变化。
- 控制台没有报错。

必须验证真实页面上的按钮。

---

## 14. 按钮灰色不一定是 CSS 问题

按钮不可点击时，先检查：

1. DOM 是否真的存在 `disabled`。
2. `disabled` 来自哪个状态变量。
3. 状态是本地推断还是服务端真实状态。
4. SSE／WebSocket／轮询是否延迟。
5. 是否有透明层挡住点击。
6. 最后才检查按钮颜色。

视觉状态应是业务状态的结果，不能把“看起来灰色”直接当成 CSS 问题。

---

## 15. 成功、错误和运行状态应分开

- 运行状态：显示真实阶段和等待时间。
- 错误：保留在当前任务工作区，说明原因和重试方式。
- 导出成功：使用短暂提示，几秒后消失。
- 页面切换：清理局部成功提示。
- 上次结果：单独保存，不被当前错误覆盖。

不要让“已导出某文件”跨到其他功能页继续显示。

---

## 16. 刷新没有变化时的排查顺序

不要马上再加一层 CSS。

应依次检查：

1. 当前打开的是完整产品还是内部结果页？
2. 当前 URL 是否属于最新启动实例？
3. 服务进程是否使用刚修改的工作树？
4. 静态资源是否由当前服务提供？
5. 是否仍连接旧端口或旧 session？
6. DOM 是否已经更新？
7. CSS 是否已经加载？
8. 最后才检查浏览器缓存。

不能通过不断提高 CSS 权重来“对抗缓存”。

## 17. 视觉资产管理

### 参考资料优先级

同一项目可能同时存在正式页面、旧截图、批注图、原始素材和 AI 草稿。发生冲突时，默认按以下顺序判断：

1. 用户最近一次明确确认的最终效果或正式资产。
2. 当前运行页面中已确认的状态。
3. 现行设计规范和锁定清单。
4. 为本次问题提供的批注截图。
5. 原始来源图，只用于理解结构、内容和风格。
6. AI 生成的草稿，只能作为新提案，不能反过来覆盖正式基准。

如果高优先级资料彼此冲突，应指出冲突并请求确认，不能自行拼成未经确认的折中版。

### 正式运行资产

- 同一视觉角色只保留一个正式文件。
- 使用稳定名称，不使用 `final-v12-final2`。
- 生产代码只引用正式资产。

### 设计参考

- 原图、草稿、授权依据放在独立参考目录。
- 明确标记为非生产资产。

### QA／测试资产

- 截图、对比图和 Demo 放在测试目录。
- 不与运行资产混放。
- 旧失败图没有回归价值时应删除；需要保留时明确写明“历史失败示例”。

### 视觉锁定记录

用户确认锁定的重要视觉，建议记录：

- 正式资产或组件名称。
- 使用位置和用途。
- 默认、悬停、展开、禁用等状态规则。
- 允许继续调整的属性。
- 禁止顺带改变的属性。
- 目标视口或响应方式。
- 人工确认日期。
- 对应 Git 提交、标签或可恢复版本。

锁定不是禁止未来重新设计，而是要求重新设计以“新方案”提出，不能在功能开发中无提示改变。

### 禁止

- 在运行目录堆积连续编号试验图。
- 从 Downloads 或临时生成目录直接引用。
- 用新文件名绕过浏览器缓存。
- 发布包携带未使用的旧视觉素材。

## 18. 标准工作流程

### 从 0 到 1

1. 理解产品、用户和主要任务。
2. 提出必要问题或声明合理假设。
3. 给出 2–3 个有差异的视觉方向。
4. 大改动优先询问是否先做草稿图。
5. 用户确认方向后实现正式代码。
6. 补齐状态、响应式和可访问性。

### 改造或修复现有 UI

1. 打开真实完整产品。
2. 确认当前源码和运行实例。
3. 复述改变项与保持项。
4. 找到唯一 DOM、CSS、状态和事件来源。
5. 修改源头并删除旧实现。
6. 搜索旧资源、重复选择器和覆盖层。
7. 验证真实操作链路。
8. 主观视觉交给用户确认。

---

## 19. 完成定义

根据任务类型选择适用项，不是每次都要机械执行全部条目。

- 用户指定的视觉目标已经出现。
- 未授权区域没有意外变化。
- 没有旧色块、残边、透明遮挡和重复圆角。
- 没有重复 DOM、重复 CSS 和重复事件。
- 按钮、关闭、拖动和滚动真实可用。
- 数据操作从点击到持久化完整通过。
- 刷新或重启后的状态符合产品要求。
- 正式资产目录没有混入试验版。
- 自动测试和人工视觉判断各自完成职责。

从 0 到 1 的草稿阶段不要求满足全部工程验收；进入正式实现后再补齐。

## 20. 什么时候应该停止继续打补丁

出现以下情况时，应停下来重新定位根因：

- 连续两次仍出现同一残边。
- `×` 看得见但点不动。
- 刷新后效果完全不变。
- 后端成功但前端没有变化。
- 为修一个问题已经需要第三层补丁。
- 无法确认用户看到的是不是当前实例。

此时说明：

```text
已确认的现象：
尚未确认的环节：
最可能的根因：
下一步最小核验：
需要用户人工判断的内容：
```

不要靠反复试错消耗时间和 Token。

### 20.1 先区分结构问题和审美问题

以下通常属于结构或实现问题：

- 轮廓没有闭合。
- 元素接错位置或悬空。
- 状态切换发生跳动。
- 点击区域被遮挡。
- 坐标在滚动后偏移。
- 清空后前端仍显示旧数据。

它们不应通过“再淡一点、再模糊一点、加阴影、换一个颜色”来掩盖。结构正确以后，再讨论是否好看。

### 20.2 使用可验证假设，而不是凭感觉连续微调

出现异常时，可以采用：

```text
现象：深色背景上出现白边。
假设：透明像素仍残留白色 RGB。
本轮只验证：关闭 CSS 滤镜并以原尺寸显示同一素材。
通过标准：白边是否仍存在。
```

一轮只验证一个主要根因，不等于创意阶段只能改变一个视觉变量。这个方法只用于诊断和精密修复。

### 通用版


## 23. 高风险视觉专项工具箱

这些专项只在对应风险出现时启用。普通文本页、简单表单或低风险样式调整不需要机械执行全部检查。

### 23.1 图层与属性作用范围

适用于透明度、滤镜、缩放、模糊、纹理、背景和复合组件。

先区分：

| 层级 | 常见对象 | 常见属性 |
|---|---|---|
| 定位层 | 整个浮窗或工具 | `top`、`left`、`right`、`bottom`、响应式位置 |
| 对象本体层 | 插图、产品图、Logo | 尺寸、裁切、主体透明通道 |
| 背景层 | 卡片底色、玻璃、宣纸、渐变 | 背景色、背景透明度、模糊、纹理 |
| 内容层 | 标题、正文、按钮、列表 | 字号、行距、间距、滚动 |
| 特效层 | 烟雾、光点、阴影、粒子 | 混合、透明度、动画、锚点 |

修改前说明属性作用于哪一层。给共同父容器设置 `opacity` 会让所有子元素一起变淡；如果只需背景半透明，应使用带透明度的背景色或职责明确的独立背景层。

“放大”也需要说明是放大整个组件、对象本体还是某一特效。附加文字或装饰超出主体时，不能为了塞入同一裁切框而缩小主体。

### 23.2 坐标空间与批注映射

适用于移动、裁切、像素修补、标注截图和局部对齐。

至少区分：

- 浏览器视口坐标。
- 页面文档坐标。
- 应用外壳或组件局部坐标。
- 背景图内部位置。
- 源图片像素坐标。

“往左一点”可能指整个组件左移、图片在容器内左移、背景裁切左移或只移动一个局部图层。高风险修改前应复述具体对象和坐标空间。

用户在截图上画的箭头使用截图坐标；正式素材可能已经缩放、裁切和偏移。像素级修补时：

1. 确认要连接或修改的端点／区域。
2. 必要时先输出带编号锚点的小预览。
3. 把截图坐标换算到源素材坐标。
4. 直接修改正式源资产，不在页面上长期叠加补线。
5. 同时检查放大图和实际显示尺寸。

### 23.3 多状态资产与动画锚点

适用于默认／悬停、开／关、展开／收起、亮／暗等多状态组件。

各状态建议保持：

- 相同画布宽高。
- 相同主体比例。
- 相同底边或指定锚点。
- 相同主体轮廓和不应变化的明暗。
- 只改变需求允许变化的部分。

可以通过叠帧、差分或半透明闪烁检查主体漂移。文字、烟雾、光效等附加层应独立控制，不能迫使主体在不同状态中改变尺寸。

需要检查快速反复触发是否会累积动画实例、重复图层或中间残帧。

### 23.4 透明素材、Alpha 和白边

适用于 PNG、WebP、抠图、半透明插画和带柔边素材。

“看起来透明”不等于真正有透明通道，棋盘格也可能已经成为图片内容。至少在以下背景检查：

- 深色纯色背景。
- 浅色纯色背景。
- 真实复杂页面背景。

发现白边或矩形残留时依次检查：

1. 分别隐藏对象本体和特效层。
2. 关闭 CSS 滤镜、阴影、混合模式和整体透明度。
3. 以原始尺寸显示，排除缩放插值。
4. 检查图片是否真的包含 Alpha。
5. 检查透明像素中的 RGB 是否仍带原背景颜色。

不能用降低整张图片 `opacity` 的方式修复白边。它只会让主体和错误一起变淡。

### 23.5 图层接口与接触关系

适用于连接线、液体、光束、烟雾、装饰线和贴合对象。

透明度、模糊和发光不能代替正确的接触位置。应先以清晰、高对比方式确认起点、终点和接口，再恢复最终视觉效果。

需要检查是否悬空、穿透、接到错误轮廓或在缩放后错位。

### 23.6 多视口、显示缩放和响应式证据

至少区分：

- 浏览器视口尺寸。
- 应用外壳设计尺寸。
- 组件内部画布尺寸。
- 浏览器缩放和操作系统显示缩放。

提供或比较截图时，尽量记录视口宽高、滚动位置、浏览器缩放以及内置／外部浏览器环境。不能只根据单一窗口截图推翻整体布局。

根据目标产品选择需要检查的环境，例如桌面大屏、常见笔记本、窄窗口、125%／150% 显示缩放和高 DPI；不要求所有项目机械覆盖所有环境。

滚动应有明确责任层：浏览器外层、应用内容区、浮窗还是内部列表。不要让多层同时争抢滚轮。

### 23.7 鼠标跟随、粒子、光效和声音

只在项目包含这些效果时启用。

跟随层通常应：

- 不参与文档布局。
- 不改变页面尺寸或制造滚动条。
- 使用 `pointer-events: none`，不遮挡真实控件。
- 控制粒子数量、生命周期和内存释放。
- 在滚动、缩放和视口边缘验证坐标。

使用鼠标坐标时，不应无意混用视口坐标、页面坐标和组件局部坐标。已有认可 Demo 时，应记录关键算法和参数，在正式页面做一致性验证，而不是重新凭感觉调整。

输入框、编辑区、选择控件、禁用按钮和高频操作通常不应播放装饰音；还应考虑静音和减少动态效果偏好。

### 23.8 文字、纹理和按钮层级

纹理、纸感、颗粒和玻璃效果属于背景或装饰层，不应让文字变得凹凸、发虚或半透明。

字号建议按页面标题、主要说明、次级说明、按钮、状态与元信息建立层级，避免逐个元素凭感觉反复缩放。

按钮视觉重量由任务重要性决定，但较小的视觉按钮仍要保留足够点击区域。文案替换应使用最终确认文本，不能让旧句残留在其他位置。

### 23.9 自动检查与人工验收分工

自动化适合检查：

- DOM、尺寸和资源引用。
- 状态切换是否发生。
- 滚动责任层。
- 缺失文件和重复选择器。
- 请求、持久化和刷新恢复。

人工更适合判断：

- 画风是否统一。
- 视觉重心是否舒服。
- 半透明和动效是否自然。
- 字号、行距和阅读负担。
- 声音是否突兀。
- 实际浏览器是否妨碍任务完成。

自动截图不能替代全部审美判断；人工觉得不对时，也不应立即盲调，应先判断是结构问题还是审美取向。

### 23.10 风险修改与版本回退

重抠图、多状态资产重组、响应式重构和整体布局调整前，建议建立可恢复的 Git 提交或版本点。

已发布标签不应移动或覆盖；需要修正时建立新的提交或版本。旧试验素材不应作为“保险”继续留在生产资产目录，历史由 Git 或明确的参考归档负责。

## 24. 最终提醒

```text
视觉创意可以自由，技术实现不能靠遮盖和堆补丁。

专业词汇可以使用，但模型应承担推荐和解释责任。

用户不需要预先懂 margin、display 或具体像素值；专业词汇可以正常使用，用户在需要时询问，模型必须结合当前设计用大白话说明。

从 0 到 1 时，不要求不存在的正式页面和截图；大改动优先先看草稿，用户也可以选择直接开发。

修改现有 UI 时，如果旧实现仍然存在，新实现只是盖在上面，就不算完成。

如果后端通过但真实按钮没有通过，就不算完成。

如果只打开组件页而不是完整产品，就不算完成。
```
